# Design Guideline

会社員向け iDeCo新制度ガイド（`ideco-navi`）のデザインガイドラインです。
[docs/wireframe.md](./wireframe.md) で整理した情報設計・画面構成・優先順位を前提とし、実装済みの `src/index.css` および各コンポーネントCSSを確認したうえで、そこに存在するルールを言語化・体系化したものです。既存デザインの方向性を否定するものではなく、CSSの一貫性を保つための土台として作成しています。

その後、このガイドラインに沿ってTailwind CSS（v4）を導入し、デザイントークンの一元管理・remベースのタイポグラフィ・`clamp()`によるレスポンシブな見出し/結果表示・共通パーツの整理・`:focus-visible`によるアクセシビリティ改善を実装しました。本ドキュメントはその実装内容を反映した最新版です（実装の詳細は「13. CSS Implementation Principles」参照）。

---

## 1. Design Concept

### Visual concept
「金融機関・公的機関が発行する情報サイト」として自然に見えることを最優先とする。派手な訴求や比較・煽り型の金融広告とは一線を画し、**制度を正確に読み解くための道具**という見え方を目指す。

### Tone & Mood
- 落ち着いたネイビー×ティールの2トーン配色（実装済み）
- 余白を広めに取り、1セクション1テーマで区切る
- 数字・専門用語には必ず短い解説や根拠を添える
- 「断定しない・目安であることを明示する」トーンを一貫させる（wireframe.md 8章のUX方針を継承）

### Design principles
1. **信頼感を最優先する**：奇抜な配色・過剰な装飾は避け、公的機関のサイトに並んでも違和感のない見た目にする
2. **情報の階層を明確にする**：`SectionHeading`のアンダーライン、`Card`の枠線、見出しサイズだけで階層を示し、装飾で階層を作らない
3. **根拠を隠さない**：結果は数字だけで終わらせず、常に内訳・計算式・注意事項をセットで見せる（wireframe.md「11. Data/Result Display」に対応）
4. **一貫した最小限のパーツで構成する**：`Button` `Card` `SectionHeading` `AsyncState` `NoticeBox` など、少数の共通コンポーネントを使い回す（新しい見た目のパーツをページごとに増やさない）

## 2. Color

`src/index.css` の Tailwind `@theme` ブロックでデザイントークンを一元管理している。既存コンポーネントCSSが参照していた変数名（`--color-navy-900` 等）は `:root` でこれらへのエイリアスとして残し、値の定義元を1箇所にまとめた（二重管理の回避）。**新しい色は追加せず、既存の2トーン（ネイビー／ティール）＋グレースケール＋アンバーの構成をそのままトークン化している。**

| 役割 | 変数名（`@theme`） | 値 | 旧トークン名（`:root`のエイリアス） |
|---|---|---|---|
| Primary Color | `--color-primary` | `#10233f` | `--color-navy-900`（見出し、Header/Footer背景） |
| Secondary Color | `--color-secondary` | `#1d3f66` | `--color-navy-700`（サブ見出し、セカンダリボタンの線・文字） |
| Accent Color | `--color-accent` | `#0f7a68` | `--color-teal-600`（プライマリボタン、リンク、強調数値、アクティブ状態） |
| Accent Hover | `--color-accent-hover` | `#0c6a5a` | `--color-teal-700` |
| Accent Tint | `--color-accent-tint` | `#e7f4f1` | `--color-teal-50`（強調パネル・バッジ背景） |
| Background Color | `--color-background` | `#f6f7f9` | `--color-bg`（ページ全体の背景） |
| Surface Color | `--color-surface` | `#ffffff` | 同名（エイリアス不要） |
| Text Color | `--color-text` | `#1b2430` | 同名（エイリアス不要） |
| Muted Text Color | `--color-muted` | `#5c6472` | `--color-text-muted`（補足・キャプション） |
| Border Color | `--color-border` | `#dee2e7` | 同名（エイリアス不要） |
| Error Color | `--color-error` | `#ad6e15` | `--color-amber-600`（注意喚起と入力エラーを同じ色で表現） |
| Error Background | `--color-error-tint` | `#fbf1e2` | `--color-amber-50` |
| Success Color | 未実装 | `#0f7a68`（Accent Colorを流用する案） | 下記「設計判断のメモ」参照 |

`@theme` で定義したトークンはTailwindのユーティリティクラス（`bg-primary` `text-accent` `border-error` 等）としても利用可能になっているが、現時点では既存コンポーネントCSS側の書き換えは行っておらず、実際のJSXでの利用実績はない（トークン層としての導入にとどまる）。

### 設計判断のメモ

- **Error Colorに赤系を使わず、既存のアンバーを踏襲する**：金融サイトで赤は「損失・危険」を強く想起させるため、控えめなアンバーで「確認してください」というニュアンスにとどめている現行方針を維持する。`NoticeBox`・`AsyncState`・フォームのエラー表示（`.rd-error`）が既にこの前提で統一されているため、そのまま`--color-error`として名前を与える。
- **Success Colorは現状未実装**：計算成功時の演出や送信完了メッセージなど、現在のUIには「成功」を単独で示す箇所がない（シミュレーターの結果表示は成功時もニュートラルな`Card`のまま）。将来追加する場合は、新しい色相を増やさずAccent Color（ティール）を流用することを推奨する。ティールは既に「良い情報・進める方向」の意味で使われているため（プライマリボタン、税制メリットの番号アイコンなど）、意味的な一貫性が保てる。
- **Header/Footerの白文字系グレー**（`#c7d1de` `#aebccd` `#8ea0b6` `#d8e6e1`）は、ネイビー背景専用の読みやすさ調整用シェードであり、汎用トークン化はせず「ネイビー背景の上でのみ使う例外」として扱う。

### ダークモード
現状、明示的なダークモード対応（`prefers-color-scheme`等）は実装されていない。金融制度の解説サイトとして可読性・信頼感を最優先するため、当面はライトテーマのみを正式仕様とする。

## 3. Typography

### font-family（実装済み・変更なし）
```css
--font-heading: "Zen Kaku Gothic New", "Noto Sans JP", sans-serif;
--font-body: "Noto Sans JP", "Hiragino Sans", "Yu Gothic", sans-serif;
```
見出し・本文ともにゴシック体で統一し、30〜50代の会社員が読む「実務的な情報サイト」として違和感のない書体を維持する。

### type scale（rem実装済み）
ルートのフォントサイズはブラウザ既定の`16px`を基準とする（`html`に独自の`font-size`指定はない）。全CSSファイルの`font-size`をpx指定からrem指定に変換済み（本文は`0.9375rem`＝15px相当）。

| 用途 | rem値 | px換算 | 備考 |
|---|---|---|---|
| H1（ページ主見出し） | `clamp(1.5rem, 1.2rem + 1.5vw, 2rem)` | 24〜32px | Hero・退職所得控除ページの見出しで`clamp()`実装済み（後述） |
| H2（`.section-heading`） | `clamp(1.25rem, 1.1rem + 0.6vw, 1.5rem)` | 20〜24px | 同上 |
| H3（サブ見出し） | `1rem`〜`1.125rem` | 16〜18px | |
| リード文 | `1rem` | 16px | Hero・ページ紹介文 |
| 本文 | `0.9375rem` | 15px | `line-height: 1.8` |
| 結果の強調数値 | `clamp(1.5rem, 1.3rem + 1vw, 2rem)` | 24〜32px | `.result-value`（`src/index.css`で共通化、両シミュレーターで使用） |
| ラベル・小見出し | `0.8125rem` | 13px | フォームラベル、`result-label` |
| キャプション・注意書き | `0.71875rem`〜`0.78125rem` | 11.5〜12.5px | フッター免責文、`result-note` |

### line-height
- 本文（`body`）：`1.8`（既存踏襲。制度説明の長文でも読みやすい行間を維持）
- 見出し（`h1〜h4`）：`1.5`
- 数値（結果表示）：単位を含む1行表示が中心のため`1.2`前後を推奨
- unitless（単位なし）で指定し、親のフォントサイズ変更に追従させる

### font-weight
- 見出し：`700`固定
- 本文：`400`
- ラベル・強調テキスト・ボタン：`500`〜`700`（現状 `.field label`や`.checklist-title`は`700`、チェックボックスラベルは`500`）

### letter-spacing
- 見出し：指定なし（既定のまま）でよい
- バッジ・アイコン的な短いラベル（`.hero-eyebrow`など）：`0.04em`程度の字間を既に使用しており、今後もこの用途に限定して使う

### clamp()の活用（実装済み）
ブレークポイントごとの段差ではなく、画面幅に応じて滑らかにサイズが変化するよう、以下の3箇所に`clamp()`を実装済み。

```css
/* Hero見出し（Hero.css）、退職所得控除ページの見出し（RetirementDeductionPage.css） */
font-size: clamp(1.5rem, 1.2rem + 1.5vw, 2rem);

/* セクション見出し H2（SectionHeading.css） */
font-size: clamp(1.25rem, 1.1rem + 0.6vw, 1.5rem);

/* シミュレーター結果の強調数値（index.css .result-value） */
font-size: clamp(1.5rem, 1.3rem + 1vw, 2rem);
```

導入に伴い、上記3箇所にあった「`600px`未満でH1/H2のfont-sizeを固定値に切り替える」個別のメディアクエリは削除した（`clamp()`側で吸収されるため）。

## 4. Spacing

`src/index.css` に定義済みの8段階スケールをそのまま正式なSpacing Scaleとして採用する。

```css
--space-1: 8px;   /* 0.5rem */
--space-2: 12px;  /* 0.75rem */
--space-3: 16px;  /* 1rem */
--space-4: 24px;  /* 1.5rem */
--space-5: 32px;  /* 2rem */
--space-6: 48px;  /* 3rem */
--space-7: 64px;  /* 4rem */
--space-8: 96px;  /* 6rem */
```

### 使い分けの目安（現状の使われ方に合わせて明文化）
- `--space-1`（8px）：アイコンとテキストの間、チェックボックスとラベルの間
- `--space-2`（12px）：見出し直下の小さな余白、リスト項目間
- `--space-3`（16px）：フォーム内の縦方向のgap、本文段落間
- `--space-4`（24px）：コンテナの左右パディング、カードの内側パディング、カードグリッドのgap
- `--space-5`（32px）：フォームと結果カードの間、セクション内の中ブロック間
- `--space-6`（48px）：モバイル時のセクション上下パディング、Footer上部パディング
- `--space-7`（64px）：デスクトップ時のセクション上下パディング
- `--space-8`（96px）：現状未使用（将来、特に余白を強調したいセクションのために予約）

### 補足提案
4px単位の細かい調整（`gap: 4px`や`margin-bottom: 4px`など）がいくつかのコンポーネントCSSに直書きされている。スケールの最小単位として `--space-0: 4px` を追加すると一貫性が高まるが、既存の見た目を変えるものではないため、次回CSS整理時の軽微な改善候補として記録するにとどめる。

## 5. Layout

- **最大コンテンツ幅**：`--content-max-width: 1080px`。`.container`クラスで`margin-inline: auto`により中央寄せ
- **左右余白**：`.container`の`padding-inline: var(--space-4)`（24px）。画面幅が1080px+左右48pxを下回ると、この24pxが実質的な左右マージンになる
- **セクション間余白**：`.section`クラスの`padding-block`で統一。デスクトップ`--space-7`（64px）、768px未満は`--space-5`（32px）
- **カード間隔**：グリッド内`gap: var(--space-4)`（24px）が基本。フォームと結果カードの2カラムは`gap: var(--space-5)`（32px）
- **フォーム内の間隔**：項目間`--space-4`（24px、`SimulatorSection`）または`--space-3`（16px、`RetirementDeductionSimulator`の年/月2項目）。ラベルと入力欄の間は`6px`固定
- **Header**：高さ64px（〜600pxで56px）、`position: sticky; top: 0`で常時表示
- **Footer**：`margin-top: auto`で常に画面下部に配置（コンテンツが短いページでも浮かない）。3カラムグリッド（768px未満で1カラム）＋最下部に免責文1行

## 6. Responsive Design

現状の実装は「Mobile / Tablet / Desktop」を明確な3層のレイアウトとして作り分けてはおらず、**768px・600px・400pxの3つのブレークポイントで段階的に要素が切り替わる**設計になっている。この実態を前提に、以下のように呼称を対応づける。

| 区分 | 目安の画面幅 | 実装上の扱い |
|---|---|---|
| Desktop | 768px〜 | 基準となるレイアウト（2カラムグリッド、フル文字サイズ） |
| Tablet | 600px〜767px | グリッドは1カラム化されるが、文字サイズはDesktopと同じ（768px境界のみグリッドに影響） |
| Mobile | 〜599px | グリッド1カラムに加え、見出し等の文字サイズも縮小。400px以下ではHeaderのナビが折り返す |

### 要素ごとの変化

| 要素 | Desktop（768px〜） | Tablet（600〜767px） | Mobile（〜599px） |
|---|---|---|---|
| Navigation | Header内に3リンク横並び、高さ64px | 同左、高さ64px | 600pxでロゴ短縮・高さ56px、400pxでナビが折り返し2行（`flex-shrink:0`で高さ可変） |
| Grid | 3カラム（税制メリット）／2カラム（フォームと結果、Footer） | 1カラムに切り替え（768pxで発火） | 1カラム |
| Card | `grid-template-columns: repeat(3,1fr)`等 | `1fr` | `1fr` |
| Form | ラベル＋入力欄を2カラムの片側に配置 | 同上（グリッド自体は1カラムだが個々のフォームは元々縦積み） | 入力欄幅100%、ボタンも`width:100%` |
| Button | 内容に応じた可変幅 | 同左 | Hero内のCTAのみ縦積み＋幅100% |
| Typography | H1: 32px, H2: 24px（`clamp()`上限） | 画面幅に応じて連続的に縮小 | H1: 24px、H2: 20px（`clamp()`下限）付近まで連続的に縮小 |
| Section spacing | `padding-block: 64px` | 768px未満のため`padding-block: 32px`に切り替わる | 同左（32px） |

### 今後の改善候補
- H1・H2・結果の強調数値は`clamp()`化により、Tablet帯を含めて画面幅に応じた連続的なサイズ変化になった。一方でGrid（カード・フォームの列数）は引き続き768px単独のブレークポイントで切り替わるため、「Tablet帯はグリッドが1カラムになった直後」という体感はまだ残る。意図的な設計だが、今後より細かく調整する場合はこの帯域向けの調整余地がある。

## 7. Components

既存コンポーネント（`src/components/`）に対応するルールを整理する。**現在のプロジェクトに存在しないコンポーネントは実装を作らず、将来追加する場合のルールとしてのみ記載する（明記あり）。**

### Header
- 役割：サイト全体のナビゲーション。現在地の表示
- サイズ：高さ64px（Mobileで56px）
- 背景：Primary Color（`--color-navy-900`）、文字は白〜`rgba(255,255,255,.75)`
- Border：下端に`1px solid rgba(255,255,255,.08)`
- Hover：ナビリンクは`rgba(255,255,255,.75)`→`#fff`
- Focus：`:focus-visible`でAccent Colorの2pxアウトライン（`src/index.css`にグローバル定義、9章参照）
- Active（現在地）：下線（`border-bottom: 2px solid var(--color-accent)`）＋文字色`#fff`

### Footer
- 役割：サイト概要の再掲、主要ページ導線、出典表示、免責文
- 背景：Primary Color、3カラムグリッド（768px未満で1カラム）
- 余白：`padding-block: var(--space-6) var(--space-4)`
- 最下部：`border-top: 1px solid rgba(255,255,255,.12)`で区切った免責文（1行、`--color-text-muted`相当の明るいグレー）

### Button（`.btn` / `Button`コンポーネント）
- 役割：主要な行動（送信・ページ遷移）を示す
- サイズ：`min-height: 44px`（タップ領域確保）、左右`padding: 26px`
- Border radius：`--radius`（4px）。金融サイトとして角を丸めすぎない
- Variant：
  - Primary：背景Accent Color、白文字。Hoverで`--color-accent-hover`
  - Secondary：背景透明、Secondary Colorの文字とボーダー。Hoverで`--color-accent-tint`背景
- Disabled：背景`--color-border`、文字`#93999f`、`cursor: not-allowed`
- Shadow：なし（枠線と塗りのみで区別し、影による装飾は使わない）

### Link
- 通常テキストリンク：Accent Color（`--color-teal-600`）、下線なし（`SourceList`など出典リンクのみ下線あり）
- Hoverの色変化は文脈（Header/Footerの白系リンク、本文中のAccent系リンク）ごとに定義済み

### Card（`.card` / `Card`コンポーネント）
- 役割：関連情報のまとまりを視覚的に区切る（税制メリット、結果表示、タイムライン内訳など）
- 背景：Surface Color、`border: 1px solid var(--color-border)`
- Border radius：`--radius-lg`（8px）
- 内側パディング：`--space-4`（24px）
- Shadow：なし。強調したいカード（結果表示など）は影ではなく`background: var(--color-accent-tint)`＋`border-color: var(--color-accent)`で表現する（現行の`.simulator-result` `.rd-result` `.reform-card`が一貫してこの方式）

### Section（`.section` / `SectionHeading`）
- 役割：ページを意味のかたまりごとに区切る最小単位
- 縦方向の余白：`padding-block: var(--space-7)`（Mobileで`--space-5`）
- 見出し（`.section-heading`）：24px・下に3px×36幅のAccent Colorの短い下線。装飾はこの下線のみに限定し、過剰な飾りを増やさない

### Heading（h1〜h4）
- 色：Primary Color固定
- フォント：`--font-heading`
- サイズ階層は3章のtype scaleに準拠

### Form / Input / Select
- ラベル：入力欄の直上に配置、13px・700・Text Color
- 入力欄：高さ44px、`border: 1px solid var(--color-border)`、`border-radius: var(--radius)`、内側左右`12px`
- Focus：Header等と同じグローバルな`:focus-visible`（Accent Colorの2pxアウトライン）で統一。以前は入力欄ごとに個別定義していたfocusスタイルは重複のため削除し、グローバル定義に一本化した
- チェックボックス：`width/height: 18px`、`accent-color: var(--color-accent)`
- 説明文（`.field-hint`）：入力欄の下に11.5px・Muted Text Colorで補足（例：「年収は税制メリットの概算にのみ使用」）
- `.field` `.field-hint`は掛金シミュレーション・退職所得控除シミュレーターの両方で使う共通クラスとして`src/index.css`に集約済み（コンポーネント個別CSSでの重複定義を解消）

### Error message
- 色：Error Color（アンバー系）、背景`--color-error-tint`
- 見せ方：フォーム直下に枠付きブロックで表示し、色だけに頼らず「入力エラー：」という文言を必ず前置きする（`role="alert"`をあわせて使用）
- Notice系（後述）と同じ配色に揃えることで、「注意が必要な情報」という一貫したシグナルにしている

### Notice box（`NoticeBox`）
- 役割：制度上の重要な注意点を本文から視覚的に切り離して伝える
- 背景：`--color-error-tint`、左端`4px`のAccent border（Error Color）、他3辺は`1px`
- タイトル：Error Colorで太字。「重要：〜」のように結論を先頭に書く
- 本文：Text Color、複数段落は`margin-top`で区切る

### Result display（結果表示）
- 「11. Data / Result Display」に詳細を記載。共通ルールとして、強調カード＋内訳（`dl`のdt/dd）＋注意書きの3点セットを崩さない
- `.result-value`（強調数値）・`.result-breakdown` / `.result-breakdown-row`（内訳テーブル）・`.result-label` `.result-note`は`src/index.css`の共通クラスとして実装済み。掛金シミュレーション・退職所得控除シミュレーターの両方が同じクラス名を参照しており、見た目のズレが起きない構成になっている

### FAQ（`FaqItem` / `FaqSection`）
- 一覧はカード化せず、`border-bottom`区切りのフラットなリスト
- 質問行：クリックでアコーディオン開閉。「Q.」の接頭辞をAccent Colorで表示
- アイコン：開閉は「＋/－」型の自作アイコン（画像なし、CSSの疑似要素で表現）
- 回答：`--color-text-muted`、開いたときのみ表示（アニメーションなし＝即時表示）

### 現状存在しないが、将来必要になった場合のルール（架空実装はしない）
- **Toast / スナックバー通知**：未実装。追加する場合はSuccess Color（Accent Colorを流用）を背景に使い、Notice boxと同じ角丸・余白ルールを踏襲する
- **モーダル / ダイアログ**：未実装。追加する場合もShadowは最小限にし、Cardと同じborder基調のスタイルを優先する
- **Tooltip**：未実装。専門用語の補足は現状`field-hint`や本文内の説明で対応しており、当面はTooltipを導入しない方針を推奨する

## 8. Form Design

掛金シミュレーション（`SimulatorSection`）と退職所得控除シミュレーター（`RetirementDeductionSimulator`）を主対象に、30〜50代の会社員が迷わず入力できることを目的とする。

- **Label**：入力欄の直上、太字・13px。「年収（円）」のように単位をラベル内に含める
- **Input**：数値入力は`type="number"`＋`inputMode="numeric"`。高さ44px以上でタップしやすくする
- **Select**：チェックボックス2択（企業年金の有無／企業型DCの有無）のように、専門的な条件分岐はテキストで丁寧に選択肢を説明する（「DB（確定給付企業年金）など、企業型DC以外の企業年金がある」のように略語だけで終わらせない）
- **説明文**：判断に迷いやすい項目（年収の使い道、加入期間の考え方）には`.field-hint`で1文の補足を必ず添える
- **単位**：金額は「円」、期間は「年」「か月」をラベル・結果表示の両方に明記し、数字だけを裸で出さない
- **入力例／初期値**：フォームは空欄スタートではなく、意味のある初期値（掛金シミュレーション：40歳・年収600万円・毎月2万円／退職所得控除：20年6か月）をあらかじめ入れておき、操作方法を推測しやすくする
- **エラー表示**：Error Colorのブロックで「入力エラー：」から始まる具体的な文言（例：「月数は0〜11の範囲で入力してください。」）を表示。数値のみ・色のみで判断させない
- **結果表示**：送信方式（掛金シミュレーション：ボタン押下）／即時反映方式（退職所得控除：入力するたびに自動更新）のどちらであっても、結果カードは常に入力欄の隣（Desktop）または直下（Mobile）に配置し、入力と結果の対応関係を視覚的に切らさない

## 9. Accessibility

WCAGの考え方を参考にしつつ、過剰に複雑な独自ルールは設けない。

- **コントラスト**：本文（`--color-text` #1b2430）と背景（`--color-background` #f6f7f9 / `--color-surface` #fff）はWCAG AA基準を満たす濃さを確保済み。Muted Text Color（`#5c6472`）も背景白地でAA相当を確保。今後新しい配色を追加する際は、本文サイズでコントラスト比4.5:1以上を目安にする
- **Focus表示**：`a:focus-visible, button:focus-visible, input:focus-visible, select:focus-visible, [tabindex]:focus-visible`にAccent Colorの2pxアウトラインをグローバルに実装済み（`src/index.css`）。マウス/タップ操作では表示されず、キーボード操作時のみ表示される。Header/Footerのリンクを含むサイト全体のリンク・ボタン・入力欄で統一済み
- **キーボード操作**：FAQの開閉・シミュレーターの入力・ページ遷移はすべて標準的な`<button>` `<a>` `<input>`要素で実装されており、追加のJS制御なしにTab操作・Enter操作が可能
- **Form label**：すべての入力に`<label htmlFor>`を対応付け済み（例：`sim-age` `rd-years`）。チェックボックスもラベルで囲み、クリック領域を広げている
- **Error message**：`role="alert"`を使用し、視覚的な色（アンバー）だけでなく「入力エラー：」というテキストで明示。入力欄には`aria-describedby`でエラー文言を関連付け済み
- **リンク**：リンクテキストは「トップページへ戻る」のように遷移先が分かる文言を使い、「こちら」のような曖昧な表現を避ける
- **ボタン**：ラベルは行動が分かる具体的な文言（「入力内容で確認する」）を使用
- **文字サイズ**：本文は15px（0.9375rem）を下限とし、これより小さい文字（注意書き等）は11.5px程度までに留め、長文には使わない
- **タップ領域**：ボタン・入力欄はいずれも`min-height: 44px`を確保（Apple/Googleのタップターゲット推奨値に準拠）

## 10. Content Design

金融制度の解説サイトとして、文章表現のルールを整理する。

- **専門用語**：初出時は必ず日本語での言い換えや補足を添える（例：「企業型DC（企業型確定拠出年金）」のように、略語単独では使わない）。すでに全ページでこの書き方が徹底されている
- **見出し**：体言止め、または「〜とは」「〜について」のように内容が一目で分かる形にする。煽り文句・疑問形の釣り見出しは使わない
- **説明文**：1文を長くしすぎない。「〜です。」「〜ます。」の常体で統一し、箇条書きにできる情報は文章に埋め込まず箇条書きにする
- **箇条書き**：チェックリストやFAQの見せ方のように、比較・確認事項は文章より箇条書きを優先する
- **注意事項**：本文中に埋め込まず、`NoticeBox`や`.result-note`のような専用の見た目に分離し、読み飛ばされにくくする
- **重要情報**：断定を避け、「〜の対象になります」「〜が考えられます」「〜な場合があります」のように、制度上の可能性を正確に表す言い回しを徹底する（「絶対に得」「必ず〜」のような断定表現は使わない）
- **参考情報**：制度の数値や計算根拠には、必ず`SourceList`で一次情報（国税庁・厚生労働省・iDeCo公式サイト）へのリンクを添える

## 11. Data / Result Display

シミュレーション結果は「数字だけを大きく見せて終わり」にしないことを最重要ルールとする。

- **結果の強調**：結果カードの背景をAccent Tint（`--color-accent-tint`）にし、枠線をAccent Colorにすることで、他のカードと視覚的に区別する（影は使わない）。強調数値のfont-sizeは`clamp(1.5rem, 1.3rem + 1vw, 2rem)`（`.result-value`、`src/index.css`）とし、画面幅に応じて滑らかに変化する
- **金額表示**：円単位は`toLocaleString()`でカンマ区切り＋「円」を明記。あわせて万円換算（例：「（1,500万円）」）を小さめの文字で併記し、桁の大きい数字でも直感的に把握できるようにする
- **単位**：金額・年数・月数のいずれも数字の直後に単位を明記し、単位のない裸の数字を表示しない
- **計算根拠**：結果の直下に、`dl`（definition list）形式で「入力条件 → 判定区分 → 計算式」の内訳を必ず表示する。退職所得控除シミュレーターの「①調整前 → ②調整の内訳 → ③調整後」のように、複数ステップある場合は番号を振って順序を明示する
- **注意事項**：結果カード内に`.result-note`として、「概算である」「実際の金額は異なる場合がある」旨を必ず併記する。とくに重要な注意（重複期間の調整など）は`NoticeBox`で独立させ、結果の近くにも要約を残す
- **ローディング／エラー**：APIデータに依存する結果表示（掛金シミュレーション、制度改正セクション等）は`AsyncState`でローディング中／エラー時の文言を明示し、フォーム自体をデータ取得完了まで表示しない

## 12. Visual Rules

- **Border radius**：小さい要素（ボタン、入力欄、注意ブロック）は`--radius`（4px）、カード・パネル・テーブルなど面積の大きい要素は`--radius-lg`（8px）。バッジ（`.hero-eyebrow`等）のみ`999px`の丸みを使用し、それ以外で丸角を強調しすぎない
- **Shadow**：全面的に不使用。階層は色（枠線・塗り）とレイアウトの余白だけで表現する。金融サイトとして「浮いた」印象を避けるための意図的な選択であり、今後も維持する
- **Border**：`1px solid var(--color-border)`を基本とする。強調時のみAccent Colorに切り替える（太さは変えない。Notice boxのみ左端4pxのアクセントボーダーを例外的に使用）
- **Icon**：画像・アイコンフォントは使わず、CSSの疑似要素と文字（「✓」「＋」「Q.」等）で最小限に表現する。装飾目的のアイコンは追加しない
- **Image**：現状、装飾目的の画像・写真は使用していない。今後追加する場合も、制度説明に関係のない装飾的な画像は避け、図解が必要な場合は表・リストなどテキストベースの表現を優先する
- **Illustration**：未使用。金融・信頼性を重視するサイトの方向性上、イラストによる親しみやすさの演出は行わない方針とする
- **Divider（区切り線）**：セクション間はpadding（余白）で区切ることを基本とし、線は「Header下端」「カード内の項目区切り」など、情報のまとまりを示す最小限の箇所にのみ使用する

## 13. CSS Implementation Principles

Vite + React + TypeScript構成に、**Tailwind CSS（v4、`@tailwindcss/vite`）をデザイントークン層として導入済み**。コンポーネント単位でCSSファイルをimportする既存構成は維持しており、Tailwindのユーティリティクラスですべてを書き直す方針は採っていない。

### Tailwindの位置づけ
1. **`@theme`をデザイントークンの正とする**：`src/index.css`の`@theme`ブロックで色・フォントのトークン（`--color-primary`等）を定義する。既存コンポーネントCSSが参照していた変数名（`--color-navy-900`等）は`:root`でこれらへのエイリアスとして残し、**値の定義元を`@theme`の1箇所のみにすることで、TailwindとCSS変数の二重管理を避けている**
2. **構造的なCSSはコンポーネントCSSファイルのまま維持する**：グリッド、カードレイアウト、FAQのアコーディオン、フォームの並びなどコンポーネント固有の複雑なスタイルは、既存の「1コンポーネント（.tsx）＝1CSSファイル」の構成のまま実装する。Tailwindユーティリティへの一括置き換えは行っていない
3. **現時点ではJSX側でTailwindユーティリティクラスは未使用**：`@theme`で定義したトークンは`bg-primary`等のユーティリティクラスとしても利用可能だが、今回はトークン層の導入にとどめている。今後、新規に追加するUIで`gap-4`のようなレイアウト用ユーティリティを直接使うことは妨げないが、既存クラスと同じ見た目を二重に定義しないこと
4. **Tailwindの基本リセット（Preflight）と既存の手動リセットが重複している**：`* { box-sizing: border-box }`等、`src/index.css`内の既存リセットとTailwind Preflightで同じ内容が重複している箇所があるが、値が同一で見た目に影響しないため、リスクを避けて既存リセットはそのまま残している

### CSSの原則（既存踏襲・実装済み）
5. **remを基本単位にする**：全CSSファイルの`font-size`をrem指定に変換済み（3章参照）。ボーダー幅（1px）やアイコンの微調整（1px単位の疑似要素）はpxのままでよい
6. **clamp()は「意味のある可変幅」がある箇所にのみ使う**：H1・H2・結果の強調数値の3箇所に実装済み（3章・11章参照）。それ以外のfont-sizeへの乱用はしない
7. **line-heightは単位なしで指定する**：`line-height: 1.8`のように数値のみを指定し、`px`指定は行わない
8. **Spacing Scaleを厳守する**：`--space-1`〜`--space-8`（8/12/16/24/32/48/64/96px）の外の値（例：`13px` `18px`など）は「コンポーネント固有の微調整」としてやむを得ず使う場合のみ許容する
9. **共通パーツはコンポーネント単位CSSから`index.css`へ集約する**：フォーム（`.field` `.field-hint`）と結果表示（`.result-value` `.result-label` `.result-note` `.result-breakdown` `.result-breakdown-row`）は、掛金シミュレーションと退職所得控除シミュレーターの両方で使う共通クラスとして`src/index.css`に集約済み。以前は2つのコンポーネントCSSに同じ内容がほぼ重複していた
10. **セレクタの詳細度を上げすぎない**：クラスセレクタ1階層を基本とし、`.a .b .c`のような深いネストは避ける（`.rd-example2-card .result-breakdown`のような2階層までのスコープ限定は許容範囲として実装済み）
11. **`!important`を使わない**：詳細度の管理で解決できない場合は、セレクタやCSSの読み込み順を見直す。現状のコードベースに`!important`は存在しない
12. **レスポンシブはデスクトップを基準にmax-widthで縮小する方針を維持する**：プロジェクト全体で一貫しているため、min-width方式に混在させない
13. **保守性**：計算ロジック（`utils/`）とUI（`components/`）を分離する既存方針と同様に、CSSも「共通パーツ（`index.css`）」と「コンポーネント固有のスタイル」を分け、あるコンポーネントのCSSファイルにしか定義されていないクラスを別コンポーネントのJSXから参照しない（9番の集約により、退職所得控除ページが別コンポーネントのCSSに依存していた箇所は解消済み）

## 14. Design Decision

「30〜50代の会社員」「金融・制度情報」「iDeCo」「シミュレーター」というサイト特性から、以下の判断を行っている。

- **なぜ落ち着いたカラーにするのか**：iDeCoは老後resourcesに関わる制度であり、ユーザーは「正確な情報かどうか」を無意識に外見から判断する。派手な配色や若年層向けサービスのようなビジュアルは、情報の信頼性そのものを疑わせるリスクがある。ネイビー×ティールという2トーンに絞ることで、公的機関・金融機関のサイトと並べても違和感のない印象を作っている。
- **なぜ文字を読みやすくするのか**：対象が30〜50代であり、老眼が始まる年代も含まれる。本文15px・行間1.8という現状の設定は、小さすぎる文字による離脱を防ぐための意図的な選択であり、今後も「読みやすさ」を優先度の高い制約として扱う。
- **なぜ情報の優先順位を重視するのか**：iDeCoの制度は「iDeCoとは」から「2026年12月の改正」「自分の場合の確認事項」まで前提知識の積み上げが必要で、順序を誤ると理解できない。wireframe.mdで整理した「基礎→改正→確認事項→シミュレーション→FAQ」という順序をデザイン上も崩さず、専門用語が出る前に必ず前提知識のセクションを置く構成を維持する。
- **なぜ結果表示を明確にするのか**：本サイトの結果（掛金・退職所得控除額）はいずれも「目安」であり、断定的な数字の独り歩きは実害（誤った資産形成の判断）につながりうる。そのため、金額を大きく見せる一方で、必ず内訳・計算式・注意事項をセットで表示し、「なぜこの金額になったか」を読み手が自分で検証できる状態を維持することを、デザイン上の最優先ルールとしている。
